JioSTB Modification Session

Minimal activity report

Device: Jio JMSB200Av2 (label); Android reports JMSB200A / MSTB.

Build: Jio/4KOTTSTB/MSTB:11/25.1.9/1:user/release-keys
Security patch: 2024-02-05 · Kernel: 5.4.125

Purpose: enable ADB, reduce unwanted launcher/advertising behavior, investigate bootloader unlocking and possible root access.

This report records the steps and observations described in the session; it is not independent hardware validation.

Stage 1 — ADB and device setup

Stage 1 used the TR-069/GenieACS workflow to provision debugging and then ADB commands to configure the Android side.

  • Enabled network ADB (TCP port 5555) and set a long debugging-validity value.
  • Disabled OTA/update components and cleared staged update files, as reported by the script.
  • Preserved the TR-069 client so it could re-assert ADB settings after reboot.
  • Installed Monet Launcher and Shevery; set Monet as the home app and disabled the stock launcher.
  • After a factory reset, ADB was re-enabled by repeating the provisioning workflow.

“Stage 1” here means the repository’s ADB/provisioning setup. It is distinct from bootloader unlocking and does not itself provide root.

Networking and ACS setup

The STB was connected directly to the PC over Ethernet for an isolated local link. The PC provided DHCP for 192.168.50.0/24; the STB received 192.168.50.3 and the PC used 192.168.50.1.

  • Initially, a custom primary DNS zone for jio.com returned the ACS override but caused other Jio names to fail.
  • The zone was changed to conditional forwarding to the home router, retaining acs.oss.jio.com → 192.168.50.1.
  • Checks then returned the local ACS address for acs.oss.jio.com and a public address for www.jio.com.
  • Packet capture confirmed the STB queried the override and connected to the PC on TCP 8443.

A separate host DNS lookup later showed a public ACS address; the session diagnosed that as a host resolver path distinct from the STB’s local DNS path.

Errors and troubleshooting

  • GenieACS initially found no device because the STB had not yet reached the ACS chain; packet captures later established that DNS and TLS traffic were reaching the PC.
  • The doctor check warned that host DNS resolved ACS publicly even while the STB’s direct query received the local override.
  • ADB was sometimes closed or initially unauthorised after reboot/factory reset; after the STB accepted the host key, ADB became available.
  • A JHS post-setup attempt used a stale IP and printed misleading success-style messages despite “device not found.” A later run against 192.168.50.3 completed; JHS-specific CLU commands were not part of the JMSB Stage 1 workflow.
  • Technitium’s zone editor caused confusion between replacing a primary zone and using conditional forwarding.

Stage 2 — bootloader and root investigation

The bootloader procedure is separate from Stage 1. The repository’s PoC uses the Android settings/Zygote pathway associated with CVE-2024-31317 to call a privileged BootEnv helper and alter/read U-Boot environment values.

  • A read run logged the initial lock=10101000, an empty lock_state, and SELinux as enforcing.
  • The user reports that bootloader unlocking was later confirmed. The pasted console also showed a lock-value transition, though that transition was not present in the saved read log.
  • pull_boot.sh successfully extracted the active-slot boot image (boot_a, 64 MiB) to the PC.
  • Magisk patching/flashing was not completed in this session. The user had not confirmed a working flash transport or recovery method.

Stage 2 refers to unlocking and the subsequent boot-image/root path—not an accomplished Magisk root. The maintainer said unlock works on this model, but warned fastbootd lacks USB-host support, making further bootloader operations difficult.

Current state and next investigation

  • ADB over Ethernet had been working at 192.168.50.3:5555; it may need Stage 1 again after factory reset.
  • Monet/Shevery and update-service state were configured by Stage 1, but launcher/app persistence after reset was previously an issue.
  • A stock boot image was extracted. No Magisk-patched image was flashed; root is therefore not established by the session evidence.
  • Fastbootd USB-host limitations are the main unresolved obstacle. USB-A-to-USB-A should not be assumed to work; confirm the device’s USB role/transport before connecting or flashing.

For tomorrow’s testing, the GenieACS, MongoDB, and Technitium containers were stopped. The temporary dnsmasq DHCP process was not stopped because sudo required an interactive password; the user was given sudo kill 131136 to stop it.

No partition was flashed as part of the recorded session. Keep the extracted stock image and verify recovery/transport before any write operation.
